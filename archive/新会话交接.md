## 🔑 这台设备的 root 机制（重要，之前记录错了）

**root 来自 `init_boot` 分区，不是来自 `boot` 内核。**

### 证据（2026-10-07 实测）

`init_boot_a` 的 ramdisk 内容（用 magiskboot 解开）：

```
header_ver 4, KERNEL_SZ 0, RAMDISK_SZ 3,079,899 (2.94MB), RAMDISK_FMT lz4_legacy

ramdisk 内文件：
  init                607 KB   ← 被替换成 SukiSU 的 wrapper
  init.real          2.81 MB   ← 原始 init
  kernelsu.ko         390 KB   ← LKM 本体（这才是真正的 root 驱动）
  stock_image.sha1     40 B    ← 记录原厂内核镜像的 sha1
  debug_ramdisk/ dev/ metadata/ mnt/ proc/ sys/ system/ second_stage_resources/
```

LKM 由 `init` wrapper 在启动时 `insmod`，之后才 exec `init.real`。

### 交叉验证

当前跑官方内核时，`dmesg` 的模块列表里出现：

```
mimon(O) ... unfairmem(O) kernelsu(O) [last unloaded: ufs_ffu(O)]
```

`(O)` = out-of-tree module → **`kernelsu` 是以模块形式被加载的**，
而 `boot` 分区 md5 与 `stock-boot.img` 完全一致（纯官方内核，无内置 KSU）。
两者互证 → 确认 root 来自 init_boot 的 `kernelsu.ko`。

### 结论（SukiSU 5.15+ 的机制）

| 分区 | 角色 |
|---|---|
| `boot` | 只放内核 `Image` |
| `init_boot` | **放 root**：改造过的 init + kernelsu.ko |

→ **刷 `boot` 分区不会影响 root。** 用户 2026-10-07 的说明正确。

### ⚠️ 由此产生的一个新问题：双重 KSU

我们编的内核是把 KSU **编进内核**的（`CONFIG_KSU=y`，跑了 `setup.sh` 集成）。
实测我们的 Image 里有 **811 处** `ksu_*` / `KernelSU` 符号。

而 init_boot 会去 `insmod kernelsu.ko` → 可能变成两个 KSU 实例。

**好消息**：`kernelsu.ko` 里内建了自检，实测字符串为：

```
/__w/SukiSU-Ultra/SukiSU-Ultra/kernel/runtime/ksud_integration.c
KernelSU may be already loaded in kernel, skip!
```

即 **.ko 检测到内核里已有 KSU 时会主动跳过加载**。这是 SukiSU 官方设计的兼容路径。

**残留不确定性**：不确定它的检测方式（查 `/sys/module/kernelsu`？还是查符号？）。
内置 KSU 不会在 `/sys/module/` 下出现（已实测），所以若它只查 sysfs 则检测不到。
即便如此，最坏结果也只是 .ko 加载失败（重复注册 hook 被拒），
**内置 KSU 仍在工作，root 不会掉**。

## ⚠️ 三条必须记住的教训

### 1. 不要用 `getprop` 判断这台设备的 BL / 验证启动状态

设备装了 `YH_YC`（月虹一键隐藏）+ `playintegrityfix` + `tricky_store`，
它们会伪造这些属性：

```
getprop ro.boot.flash.locked      → 1        （假的）
getprop ro.boot.verifiedbootstate → green    （假的）
```

**真实值要读 `/proc/bootconfig`**（resetprop 改不到它）：

```
androidboot.vbmeta.device_state = "unlocked"   ← BL 实际已解锁
androidboot.verifiedbootstate   = "orange"
androidboot.slot_suffix         = "_a"
androidboot.veritymode          = "enforcing"
```

### 2. 绝不整包 `flash_all`

会触发 ARB，**不可逆**。本项目回滚**只用 boot 分区**。
另：`ro.boot.anti` 为空 = **ARB 状态 UNKNOWN**，按高危处理，
不要刷任何比当前版本旧的官方整包。

### 3. `kernel_dtb` 已被 AK3 丢弃 —— 这是最大的未实测项

原厂 boot 里带一个 `kernel_dtb`（19.3MB ~ 66.7MB）。
已验证它是**空占位**（DTB 头声明 72 字节，其余 99.9999% 零填充），AK3 删掉它是对的。
但**没有实测过** —— 若刷完卡一屏，**这是第一嫌疑点**。

## 🔧 如果 root 真的出问题（低概率）

**不要慌，也不要动 boot。** root 在 init_boot 里，与内核无关。

1. **SukiSU Ultra 管理器里重装/修复**（它会重打 init_boot）
2. 若管理器进不去：用 Horizon 刷回 `stock-boot.img` 先恢复开机
3. 最坏情况：重新用 SukiSU 打一次 init_boot
   （`ksud boot-patch` 或管理器内的"安装"按钮）

⚠️ 注意：**不要**用 `ksud boot-restore` 顺手把 init_boot 还原成官方——
那会永久丢掉 LKM 的注入点，得重新打一次。
