# 卡第一屏根因 —— 最终定论（2026-10-08 手机端 agent 实测）

> 全部数值来自本次命令输出。设备：pudding / slot _a / 当前内核 Jianke 6.12.111。
> PC：<BUILD-HOST> / WSL Ubuntu-24.04。工作目录 `C:\kd\`、`/root/pudding-kernel/`。

## 0. 结论

**V1/V2 卡第一屏 = 我方内核导出符号的 ABI CRC 与设备厂商模块要求不符，
厂商显示模块（msm_drm 等）拒载 → 显示栈起不来 → XBL splash 永不交接。**

由**三个因素叠加**造成，缺一不可（§4 逐项实测）。三处一起修后，
**ABI 与设备厂商二进制 100% 对齐**（§3 两个独立基准 DIFF 均为 0）。

## 2. 最终验证：两个独立权威基准，DIFF 全部归零

用真实 `msm_drm.ko` 的 ELF `__versions` 段（851 个符号的 modversions CRC 表）：

```
修复前: MATCH 230  DIFF 471  MISSING 150
修复后: MATCH 701  DIFF   0  MISSING 150   ← DIFF 归零
```
> MISSING 150 全是其它 vendor 模块导出的符号（`drm_dp_*`/`hdcp*`/`gh_*`/`synx_*`/`llcc_*`…），
> 属模块间依赖，正常。

用 AOSP 官方 ABI 追踪文件 `gki/aarch64/abi.stg`（同 commit `7e73c6dc7`，10554 个带 CRC 的符号）：

```
修复前: MATCH 3545  DIFF 7009
修复后: MATCH 10554 DIFF    0  MISSING 0   ← 100% 完全一致
```

**结论：修复后我方内核导出的 ABI 与设备厂商二进制要求完全一致。**

## 3. 根因分解（三条，缺一不可）

### 3.1 `CONFIG_FUNCTION_TRACER` → `struct module` 撑大 64 字节

```
include/linux/module.h:542
    #ifdef CONFIG_FTRACE_MCOUNT_RECORD
        unsigned int num_ftrace_callsites;     ← 多出来的成员 1
        unsigned long *ftrace_callsites;       ← 多出来的成员 2
    #endif

kernel/trace/Kconfig:316-319
config STACK_TRACER          ← 我们在 diag-safe.fragment 第97行打开的
    select FUNCTION_TRACER   ← 罪魁祸首藏在这里
```

三方配置（真原厂配置从 OTA boot.img 的 IKCFG 段提取）：
```
CONFIG_STACK_TRACER          真原厂=n   Jianke=n   我们=y   ← 根开关
CONFIG_FUNCTION_TRACER       真原厂=n   Jianke=n   我们=y   ← 被 STACK_TRACER select
CONFIG_FTRACE_MCOUNT_RECORD  真原厂=无   Jianke=无   我们=y   ← 被 FUNCTION_TRACER 选中
```

**⚠️ 只 `--disable FUNCTION_TRACER` 无效** —— 会被 `STACK_TRACER` 重新 select 回来。
必须**先关 `STACK_TRACER`**（实测需两轮 olddefconfig 才拿到 `# CONFIG_FUNCTION_TRACER is not set`）。

**结构体级实测（BTF 直接量）**：
```
struct module:  能开机内核 = 1600 字节 / 75 成员
                我们(原始) = 1664 字节 / 77 成员   ❌
                我们(修复) = 1600 字节 / 75 成员   ✅ 逐成员一致
```

**为什么 `struct module` 会波及显示模块**：它是 `file_system_type->owner` 的类型，
而 `file_system_type` 出现在 `kobject_uevent_env(char*, enum, const char*, va_list)` 的
DWARF 类型展开链里 → `gendwarfksyms` 递归展开 → 类型串变 → CRC 变。
同理波及所有引用 `struct module` 的导出符号。

### 3.2 `task_struct` 的 KABI 成员布局差异

成员级比对（含位偏移）显示 `task_struct` 偏移 27520 处：
```
能开机内核 : __kabi_reserved3     ← 有名字
我们       : (匿名成员)            ← 无名（ANDROID_KABI_USE 的 union 展开）
```
来源：`include/linux/sched.h:1638-1653` 的 `ANDROID_KABI_USE(1..3)` / `ANDROID_KABI_RESERVE(4..8)`。
`task_struct` 经 `mm_struct → rcuwait → task_struct *` 出现在 `kobject_uevent_env` 的类型闭包里。

### 3.3 缺 `KBUILD_GENDWARFKSYMS_STABLE=1`（构建方式差异）

```
Documentation/kbuild/gendwarfksyms.rst:
  "... kABI stability features ... all gated behind the --stable command line flag
   and are not used in the mainline kernel. To use stable features during a kernel
   build, set KBUILD_GENDWARFKSYMS_STABLE=1."

scripts/Makefile.build:114:   $(if $(KBUILD_GENDWARFKSYMS_STABLE), --stable)
gki/README.md:                "abi.stg - the tracked ABI ... maintained by Kleaf"
```

- 正式 Android GKI 用 **Kleaf** 构建，会传 `KBUILD_GENDWARFKSYMS_STABLE=1`；
- 我们的 `pudding-kernel-kit/scripts/05-build.sh` 用裸 `make`，**从未传过**；
- 实测：同一对象加 `--stable`，`kobject_uevent_env` 从 `0x95cf741c` 变为 **`0x8bb6d45c`**（= 设备值）。

## 5. 修复方案（三处一起改，已验证）

1. **`pudding-kernel-kit/gki-fragment/diag-safe.fragment`**
   删掉第 94–98 行整段 ftrace：
   `CONFIG_FTRACE` / `CONFIG_FUNCTION_TRACER` / `CONFIG_FUNCTION_GRAPH_TRACER` /
   `CONFIG_DYNAMIC_FTRACE` / `CONFIG_STACK_TRACER` / `CONFIG_TRACER_SNAPSHOT`。
   这些「为抓卡死现场」加的项与真原厂配置相悖，正是本次卡屏原因之一。
   文件顶部「不修改任何既有符号 CRC → 对厂商 404 个 .ko 零影响」注释**与事实相反**，须同步更正。
2. **`GKI_TASK_STRUCT_VENDOR_SIZE_MAX`** 回到 `1024`（对齐真原厂）。
3. **`05-build.sh`**：所有 `make` 调用加 **`KBUILD_GENDWARFKSYMS_STABLE=1`**
   （与 Kleaf 一致；这是对齐 ABI 的关键）。

**注意**：改 `KBUILD_GENDWARFKSYMS_STABLE` 必须**全量重编**（所有对象的 CRC 都要重新生成），
增量编译无法生效（实测增量时对象未重建，CRC 不变）。
