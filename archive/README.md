## 更正说明（2026-10-08 晚）

本目录的文档写于**使用 AOSP 上游树阶段**。当时我们认为：

> V1/V2 卡第一屏 = 内核导出符号的 ABI CRC 与设备厂商模块要求不符
> 三处一起修后，ABI 与设备厂商二进制 100% 对齐 ⇒ 应该能开机

**这个结论是错的（不完整）。**

### 事实

| 阶段 | 源码树 | ABI 状态 | 实测结果 |
|---|---|---|---|
| V1 | AOSP 上游 6.12.93 | `msm_drm` DIFF **471** | ✗ 卡第一屏 |
| V2 | AOSP 上游 6.12.93 | DIFF **471** | ✗ 卡第一屏 |
| 修复版 | AOSP 上游 6.12.93 | DIFF **0**（已对齐） | ✗ **仍然卡屏** |
| **成功版** | **cctv18 6.12.69** | DIFF **0** | ✅ **开机** |

**修复版是关键反例**：ABI 已 100% 对齐（`msm_drm` DIFF=0、
`struct module` 1600/75、`kobject_uevent_env` 0x8bb6d45c），仍然卡屏。

### 真正的根因

**选了错误的源码树。** `aosp-mirror/kernel_common` 缺一整层小米/高通适配
（`GKI_HACKS_TO_FIX` / `GCMA` / `RT_SOFTIRQ_AWARE_SCHED` / `UNWIND_PATCH_PAC_INTO_SCS` 等）。

→ 完整分析见 [`../docs/WHY-CCTV18.md`](../docs/WHY-CCTV18.md)

### 那 ABI 校验白做了吗

**没有。** 它的定位要修正为：

- ABI 校验是**必要条件**，不是充分条件
- 它能排除一整类故障（模块拒载），本次成功版 670 模块零符号错误正是它的预测兑现
- 但它**不能替代「选对树」** —— 选错树时它会给你虚假的安全感

## 方案变更对照

| 项 | 规划时（10-07） | 最终（10-08） |
|---|---|---|
| 源码树 | `aosp-mirror/kernel_common` @ android16-6.12 | **`cctv18/android_gki_kernel_common` @ android16-6.12-2026-03** |
| SUBLEVEL | 93 | **69**（对齐原厂） |
| 构建入口 | 裸 `make` | **`. ./_setup_env.sh`**（提供 `KBUILD_GENDWARFKSYMS_STABLE=1`） |
| 诊断 fragment | 用 `diag-safe.fragment` | **零 fragment**（该 fragment 是 ABI 破坏源） |
| KernelSU | 内置 | **不内置**（保持 LKM） |
| 结果 | — | ✅ boot_index 365 开机成功 |

## 保留这些错误文档的理由

1. **诊断方法可复用** —— `__versions` 段解析、BTF 结构体比对、cross-check 两个独立基准，这些手段本身是对的
2. **失败模式可参考** —— 下次遇到"卡第一屏"时有对照样本
3. **避免重复踩坑** —— 特别是"ABI 全过 ≠ 必定开机"这条教训
