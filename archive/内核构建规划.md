# Xiaomi 17 (pudding) 第三方内核构建规划

> 目标：为你手上这台 **Xiaomi 17 / pudding / SM8850(canoe)** 构建一个"像现在这样"的第三方内核
> 现状：机器当前跑的是 `6.12.111-Jianke`，已集成 KernelSU，另有自制模块（unfairmem / scene_swappiness）

---

## 一、实测结论摘要

| 项目 | 实测值 |
|---|---|
| 机型 | Xiaomi 17 (`25113PN0EC`)，代号 **pudding** |
| 平台 | Qualcomm **canoe / SM8850** 世代，arm64-v8a 8核 |
| 系统 | Android **17** (SDK 37) / HyperOS OS4.0.0.32.XPCCNXM |
| 当前内核 | `6.12.111-Jianke`，clang 19.0.1 + PGO/BOLT/LTO/MLGO，`LOCALVERSION=-Jianke` |
| Root | **KernelSU** (ksud 4.2.0, KMI 40900) |
| 页大小 | **4096 (4KB)** |
| 分区 | A/B，当前 slot **_a**；boot=96MB / init_boot=8MB / vendor_boot=96MB |
| 内核配置 | `/proc/config.gz`（已导出 `stock_kernel_config.txt`） |

### ⚠️ 最关键的一个发现
厂商预编译模块的 vermagic 是：

```
6.12.69-android16-6-4k SMP preempt mod_unload modversions aarch64
```

- KMI = **android16-6-4k**
- 而正在运行的内核是 **6.12.111**

👉 **意味着：厂商的 410 个 .ko（WiFi/音频/摄像头/充电…）是"预编译 ABI 模块"，
内核源码只是 ABI 兼容的 GKI 分支。** 你自己编的内核能不能开机、
WiFi 能不能用，**取决于 module ABI 是否完全兼容**。

这就是自制内核"能点亮"和"点亮后 WiFi 挂了"的分水岭。

## 二、可行性判断（先说风险）

| 难点 | 说明 | 风险等级 |
|---|---|---|
| 源码获取 | MiCode 官方仓库**没有** pudding 分支（已核实 404）；社区也没找到 pudding 完整源码 | 🔴 高 |
| Module ABI | 410 个厂商 .ko 必须匹配内核导出符号 CRC（MODVERSIONS） | 🔴 高 |
| CFI / LTO | 当前内核 `CFI_CLANG=y` + `LTO_NONE`；工具链必须用 clang 19 + Android 补丁 | 🟠 中 |
| AVB 校验 | vbmeta 1.2 + enforcing；刷 boot 需处理 vbmeta/disabler | 🟠 中 |
| 编译环境 | 本机 proot 只有 gcc，缺 git/clang/repo | 🟢 低（可装） |
| 刷机风险 | 变砖可救（fastboot + 备份），但要**先备份** | 🟠 中 |

**结论：技术上完全可行，但难在"源码"和"ABI 对齐"，不难在编译本身。**

## 三、四条路线（按性价比排序）

### 路线 A：源码级自编（终极目标，难度★★★★★）
1. 拿到 pudding 完整内核源码（4 个途径，见第四节）
2. 用 AOSP clang 19 工具链编译 6.12 分支
3. 复现当前内核配置（CFI/MODVERSIONS/4K页/HZ250…）
4. 集成 KernelSU（或 KSU-Next）
5. 打包 boot.img + 处理 vbmeta

**优点**：完全可控，可加自制模块
**缺点**：源码可能拿不到；ABI 对齐需要反复试

### 路线 B：GKI 官方内核 + KSU（最稳，难度★★☆☆☆）
用 Google 官方 **android16-6.12 GKI** 预编译内核，仅集成 KernelSU。
- 官方 KMI `android16-6-4k` 与厂商模块**天然匹配**
- KernelSU 已原生支持 GKI（改 boot.img 或 LKM 模式）
- **风险最低，最可能一次成功**

### 路线 C：魔改现有 boot.img（最快，难度★☆☆☆☆）
用 `KernelSU` 的 AnyKernel3 / boot 修补方式，基于现厂 boot 镜像打补丁。
- 不编译内核，只改镜像
- 适合"只想要 KSU + 定制模块"

### 路线 D：借助社区产物（省事，难度★★☆☆☆）
`2824799/droidspaces-xiaomi-17-kernel` 提供 pudding 的可刷 boot 镜像 + 补丁
（对应 OS4.0.0.9/.16/.26，你的是 .32，需确认兼容性）

## 六、阶段 0：备份（不可跳过）

```bash
# 在 KernelSU/终端中执行
mkdir -p /sdcard/6.12/backup_full
for p in boot init_boot vendor_boot dtbo vbmeta vbmeta_system; do
  dd if=/dev/block/by-name/${p}_a of=/sdcard/6.12/backup_full/${p}_a.img
done
# 备份当前内核配置源
cat /proc/config.gz > /sdcard/6.12/backup_full/config.gz
# 备份 bootconfig（cmdline）
cat /proc/cmdline > /sdcard/6.12/backup_full/cmdline.txt
```
> 已有 `ksu_backup_*`（8MB）是 KernelSU 自己的备份，**不能替代分区镜像备份**。

## 八、阶段 2：源码与配置复现

```bash
# 以参考源为例（换成实际拿到的 pudding 源码）
git clone --depth=1 -b <branch> <kernel_repo> kernel_6.12
cd kernel_6.12
# 用当前内核配置作为基线（强烈推荐）
cp /sdcard/6.12/stock_kernel_config.txt .config
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- LLVM=1 olddefconfig
```

### 必须与现内核保持一致的配置（ABI 关键）

| 配置项 | 值 | 原因 |
|---|---|---|
| `CONFIG_ARM64_4K_PAGES` | y | KMI 名称含 4k |
| `CONFIG_ARM64_VA_BITS` | 39 | ABI |
| `CONFIG_HZ` | 250 | ABI |
| `CONFIG_PREEMPT` | y | ABI |
| `CONFIG_MODVERSIONS` | y | 厂商模块 CRC 校验 |
| `CONFIG_EXTENDED_MODVERSIONS` | y | GKI 要求 |
| `CONFIG_BASIC_MODVERSIONS` | y | GKI 要求 |
| `CONFIG_CFI_CLANG` | y | ABI + 安全 |
| `CONFIG_LTO_NONE` | y | 现内核如此（改了易崩） |
| `CONFIG_MODULE_SIG` / `_ALL` | y | 签名 |
| `CONFIG_MODULE_SIG_HASH` | sha1 | 必须一致 |
| `CONFIG_ANDROID_KABI_RESERVE` | y | GKI ABI 保留段 |
| `CONFIG_GKI_DYNAMIC_TASK_STRUCT_SIZE` | y | GKI |
| `CONFIG_GKI_TASK_STRUCT_VENDOR_SIZE_MAX` | 1024 | 与 cmdline 一致 |
| `CONFIG_LOCALVERSION` | 自定义（如 `-Jianke`） | 标识 |
| `CONFIG_RANDOMIZE_BASE` | y | KASLR |

## 九、阶段 3：编译

```bash
export ARCH=arm64
export LLVM=1
make -j8 \
  CC="clang" LD="ld.lld" AR="llvm-ar" NM="llvm-nm" OBJCOPY="llvm-objcopy" \
  O=out gki_defconfig   # 或你的 defconfig
make -j8 O=out
```
产物：`out/arch/arm64/boot/Image`、`Image.lz4`、设备树 `out/arch/arm64/boot/dts/**/*.dtb`

## 十一、阶段 5：打包 boot.img

```bash
# 用 mkbootimg（AOSP 或现成脚本）
# 关键：从现有 boot_a.img 提取 header 参数，保持 base/offset 一致
magiskboot unpack boot_a.img      # 参考其 header
magiskboot repack boot_a.img new_boot.img
```
> 必须保持：kernel_offset / ramdisk_offset / tags_offset / pagesize=4096 / header version
> 建议直接复用现有 `boot_a.img` 的 header，只替换 kernel。

## 十二、阶段 6：刷入与验证

```bash
# 临时启动测试（推荐，失败可重启恢复）
fastboot boot new_boot.img

# 确认无误后永久刷入
fastboot flash boot_a new_boot.img
# 若 AVB 报错，需一并刷 vbmeta（disable verity/verification）
fastboot --disable-verity --disable-verification flash vbmeta_a vbmeta_a.img
```

### 验证清单
- [ ] 能正常开机进入系统
- [ ] `uname -r` 显示新版本
- [ ] **WiFi 能连接**（最重要，验 ABI）
- [ ] 蓝牙、音频、摄像头、充电正常
- [ ] 移动网络 / 通话正常
- [ ] KernelSU 管理器可识别

### 回滚
```bash
fastboot flash boot_a /sdcard/6.12/backup_full/boot_a.img
```
