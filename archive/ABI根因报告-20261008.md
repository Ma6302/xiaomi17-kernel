## 1. 决定性证据：CRC 对比（二进制级）

方法：用真实 vendor 模块 `msm_drm.ko` 的 ELF `__versions` 段（modversions CRC 表）
对照三个内核镜像里**实际存在的 CRC 字节**。

```
符号                  模块期望      真原厂6.12.69   Jianke6.12.111   我们6.12.93
_printk               16b5b21d     ✅            ✅              ✅
kobject_uevent_env    8bb6d45c     ✅            ✅              ❌(47ae9486)
class_create          310b6918     ✅            ✅              ❌(545b3917)
device_create         c289bf61     ✅            ✅              ❌(4fa43805)
wake_up_process       22175c71     ✅            ✅              ❌(16f11a14)
```

**真原厂与 Jianke 都导出设备要求的 CRC，只有我们没有。**
这解释了：为什么 Jianke 能开机、我们不能；也解释了为什么"卡第一屏 logo"
（msm_drm 显示模块因符号 CRC 不符无法加载 → 显示栈起不来 → splash 永不交接）。

## 2. 全量统计（msm_drm.ko 的 851 个符号）

```
MATCH   230   （多为基础标量类型：_printk/snprintf/memcpy/kfree/mutex_lock/msleep…）
DIFF    471   （引用结构体的符号：kobject_uevent_env/class_create/device_create/
                devm_kmalloc/kmalloc_caches/kthread_*/wake_up_process/
                irq_get_irq_data/of_find_device_by_node/sched_setscheduler…）
MISSING 150   （全部是其它 vendor 模块导出的符号：drm_dp_*/hdcp1_*/hdcp2_*/
                gh_*/altmode_*/synx_*/llcc_*/hfi_core_*/qcom_scm_*/cdev_tevent_*/
                mi_display_pwrkey_callback_set… → 模块间依赖，属正常，非本因）
```

**关键判读：471 个 DIFF 全是 vmlinux 核心导出符号，且"带结构体的就错、纯标量的就对"
—— 这是结构体布局/编译选项差异的典型特征。**

## 3. 根因：配置基线未对齐设备

真原厂配置**从 OTA boot.img 内嵌 IKCFG 块提取**（本次首次拿到真基线）：

```
# 提取命令（只读）
python3 ikcfg.py stock-ota-boot.img
→ gzip blob 48195 B → 解出 223653 B 配置
```

三方 ABI 关键项对比：

| 配置项 | 真原厂 6.12.69 | Jianke 6.12.111 | 我们 6.12.93 |
|---|---|---|---|
| GKI_TASK_STRUCT_VENDOR_SIZE_MAX | 1024 | 1024 | **1280** ❌ |
| TRIM_UNUSED_KSYMS | y | n | n |
| MODULE_SCMVERSION | y | y | **缺** ❌ |
| MODULE_SIG_PROTECT | y | ? | **缺** ❌ |
| MI_SCHED_EXT | y | ? | **树里不存在** ❌❌ |
| FUNCTION_TRACER / DYNAMIC_FTRACE | n | n | **y** ❌ |
| HARDLOCKUP_DETECTOR | n | n | **y** ❌ |

### 3.1 修正：不需要小米私有源码（重要纠错）

原厂配置里确有 `CONFIG_MI_SCHED_EXT=y`（AOSP ACK 树里零命中 → 原厂是 ACK + 小米补丁），
**但 Jianke 同样没有 MI_SCHED_EXT 也能开机**，所以它不是本次卡屏的原因：
```
MI_SCHED_EXT              y        <缺>            <缺>
MODULE_SIG_PROTECT        y        <缺>            <缺>
```

### 3.2 ⭐ 真正根因（逐项收敛后的唯一变量）

在 `struct task_struct` 的全部条件编译项里，**Jianke（能开机）与 我们（卡屏）
唯一不同、且确实改变结构体布局的一项**：

```
include/linux/sched.h:1490
    #ifdef CONFIG_FUNCTION_GRAPH_TRACER
        int              curr_ret_stack;     ← 往 task_struct 插入 3 个字段
        int              curr_ret_depth;
        unsigned long   *ret_stack;
```

```
CONFIG_FUNCTION_GRAPH_TRACER :  真原厂=n    Jianke=关    我们=y(开)
```

**机制链**：
`FUNCTION_GRAPH_TRACER=y` → `struct task_struct` 多 3 个字段 → 布局改变
→ 所有以 `task_struct *` 为参数的导出符号，其 DWARF 类型变了
→ `gendwarfksyms`（CONFIG_GENDWARFKSYMS=y，实测三个内核都开）重新推导出**不同的 CRC**
→ vendor 模块（msm_drm 等）在 `__versions` 里记录的期望 CRC 与之不符 → 拒载
→ 显示栈起不来 → 卡第一屏 logo。

**这个开关是我们自己的 `gki-fragment/diag-safe.fragment` 第 86/95 行打开的**，
而该文件顶部却写着「不修改任何既有符号 CRC → 对厂商 404 个 .ko 零影响」——
**注释与实测事实相反，这就是 V1/V2 两次卡屏的直接原因。**

### 3.3 次要差异（不改变 layout，但也应回归设备值）

```
GKI_TASK_STRUCT_VENDOR_SIZE_MAX  1024   1024   1280   ← 运行时参数(vendor_data_pad 数组)，
                                                        经 android_arch_task_struct_size 生效，
                                                        不改变编译期 task_struct 布局，
                                                        但对齐到 1024 更稳妥
MODULE_SCMVERSION                y      y      <缺>
TRIM_UNUSED_KSYMS                y      n      n
```
