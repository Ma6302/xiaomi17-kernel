## 0. 这一版和 V1 有什么不同

**只有一个变量**：新增「卡死强制转 panic」+ 卡点定位。内核源码、KSU、ABI 配置、LOCALVERSION 全部与 V1 相同。

| 项 | V1（卡一屏那版） | V2（本版） |
|---|---|---|
| 源码 | ACK 6.12.93 + KSU e7b0711 | **相同** |
| Image 大小 | 58,055,168 B | **58,055,168 B（逐字节同尺寸）** |
| BTF | 有 | **有** |
| vermagic | `6.12.93-android16-6-4k-Ma6302 SMP preempt mod_unload modversions aarch64` | **相同** |
| diag-safe | 原版 | **+ 卡死捕获增强** |
| cmdline | loglevel/ignore_loglevel/log_buf_len | **+ initcall_debug** |
| 采集器 | 无 oops 段 | **+ oops 分区转存 + .original 备份** |

### V2 新增的取证机制

```
CONFIG_BOOTPARAM_SOFTLOCKUP_PANIC=y        ← 调度停住 20s → panic
CONFIG_BOOTPARAM_HUNG_TASK_PANIC=y         ← D 状态挂起 → panic
CONFIG_DEFAULT_HUNG_TASK_TIMEOUT=30        ← 阈值 120s 降到 30s
CONFIG_PANIC_TIMEOUT=20                    ← panic 后 20s 自动重启
CONFIG_RCU_CPU_STALL_TIMEOUT=21            ← RCU stall 21s
cmdline: initcall_debug                    ← 逐条打印 probe，最后一条=卡点
```

**原理链**：卡死 → 强制 panic → panic 日志进 printk/ramoops → 20s 后自动重启 → 下次启动 mtdoops 把「上一轮 LAST KMSG」（含 panic 栈）写进 oops 分区 → harvester 读出 `oops.log`。

## 1. 刷入前必读

### ⚠️ 本版**预期仍会卡**（它是取证工具，不是修复版）

**这是设计意图**：卡死才会触发 panic，才有 stack trace 可抓。

### 刷入步骤

1. 打开 **Horizon Kernel Flasher**
2. 选择 `/sdcard/Download/pudding-kernel/pudding-KernelSU-Ma6302-20261008-V2-diag.zip`
3. 刷入 → 重启

### 🔑 刷完后请这样做（关键，别急着重启！）

```
1. 等 40 秒（20s panic + 20s 重启缓冲）
2. 观察：屏幕有没有变化？设备有没有自动重启一次？
   → 自动重启 = panic 已触发 = 证据已落盘 ✅
3. 如果 40s 后仍卡着不动 → 再等 30s（softlockup 可能被 CPU 隔离影响）
4. 记录现象：是否自动重启、卡在哪一屏
5. 然后：音量下+电源进 fastboot → PC 刷回
   fastboot flash boot_a stock-boot.img      ← 建议这次刷真·原厂
   或 fastboot flash boot_a boot_a.img       ← Jianke（当前基线）
6. 回滚开机后，采集器会自动跑，读：
   cat /data/local/bootlog/oops.log
   cat /data/local/bootlog/kernel.log
```

**绝对不要**在卡住时反复强制重启——每次重启都会让 oops 分区被新一轮覆盖，机会有限。

## 4. 抓到的栈怎么解读

`oops.log` 里会是这样的结构：

```
##FLAGS:N
## BOOT_INDEX:XXX
##REBOOT REASON:...
##### <时间>
<3>[   xxx.xxxxxx][ Txxx] Kernel panic - not syncing: softlockup: hung tasks
<3>[   xxx.xxxxxx][ Txxx] CPU: x PID: x Comm: xxx
<4>[   xxx.xxxxxx][ Txxx] Call trace:
<4>[   xxx.xxxxxx][ Txxx]  xxxxx+0x... 
...
```

**最重要的三行**：
1. `Kernel panic - not syncing: <原因>` → 是 softlockup 还是 hung_task 还是 rcu stall
2. `Comm: xxx` → 卡住的是哪个进程
3. `Call trace:` → 栈，第一个非通用函数就是卡点

配合 `initcall_debug` 的最后一条日志（kernel.log 里），**卡点模块**就完全确定了。
