## 1. 🔴 今天最重要的两个机制纠错（推翻旧推断）

### 纠错 1：mtdoops 写的是「本轮正常关机时的本轮日志」

oops 分区 **全部 8 条记录**的尾部都是干净关机流程：

```
Unmounting fuse path /mnt/pass_through/999/emulated
VolumeManager shutdown successed
shutdown()--, rtn: 0
```

→ 卡死的 354（V1）/ 356（V2）**没有关机路径 → 永不落盘**。
→ **旧推断「V1 活到 2.1s、卡在显示接管前」证据基础不成立，作废。**（`刷入失败深度分析` §9.3）

### 纠错 2：PSHOLD 复位会销毁现场（这是取证一直失败的根本原因）

「音量下 + 电源」触发的 PSHOLD warm reset **不走内核 reboot 路径** → 不调 `panic()` → 不触发 `kmsg_dump()` → **printk ring buffer 与 ramoops 全部随内存丢失**。

→ **「卡住 → 按键重启」这个动作本身必然销毁现场。加多少 printk / initcall_debug 都没用。**

→ 由此推论：**要拿到证据，必须让内核自己 panic 并自动重启**（不能靠按键）。而 V2 加的四项 panic 配置**实测一个都没触发**（见下）。

## 3. 🔴 根本未知（明天实验要解决的）

**我们至今无法证明我们的内核执行过。** V1/V2 零内核痕迹。

「卡第一屏 logo」只说明 **XBL 渲染的 splash 未被内核显示栈接管**，两种同样可能：

- **(a)** 内核跑起来了但内部挂起
- **(b)** **内核根本没开始执行**（ABL 加载/跳转到我们的 Image 失败）

此前所有分析都默认 (a)，**从未验证**。**这是明天实验的核心目标。**

## 4. 今天的新证据（设备端实测，全部只读）

### 4.1 三个内核的 PE 结构（proot python3 解析，权威）

| | 文件大小 | SizeOfImage | .text raw | .data raw | 说明 |
|---|---|---|---|---|---|
| stock kernel | 21,339,168 | 42,336,256 | 38,600,704 | 2,910,720 | **被截断**（PE 声明 > 文件） |
| stock kernel_dtb | 20,237,792 | — | — | — | 真 DTB 容器 |
| **我们的 V2 Image** | **58,055,168** | 62,914,560 | 40,304,640 | 17,684,992 | 完整 ✓ |
| **Jianke（zip 内）** | **70,961,664** | 79,953,920 | 39,059,456 | 31,836,672 | 完整 ✓ |
| Nanally（zip 内） | 42,527,232 | 43,253,760 | 39,518,208 | 2,943,488 | 完整 ✓ |

**重要**：`magiskboot unpack` 从 boot 分区切出的 "kernel" 是**截断的 PE**（它把 KERNEL_SZ 拆成 kernel + kernel_dtb）。所以我上一轮用的「Jianke 内核 21,273,504 B」是**错的**，正确的是 zip 里的 **70,961,664 B**。

### 4.2 内核格式三者一致（排除「格式不对」）

```
stock kernel : 4d5a40fa (MZ) … 0x38 = "ARMd@"
Jianke Image : 4d5a40fa (MZ) … 0x38 = "ARMd@"
我们的 Image : 4d5a40fa (MZ) … 0x38 = "ARMd@"    ← 一致
```

### 4.3 `d00dfeed` 不是差异点

| | d00dfeed 偏移 | 内容 |
|---|---|---|
| 我们的 Image | 22,149,056 | **72 字节空占位 DTB**（totalsize=72, ver=17） |
| Jianke Image | 21,273,504 | **完全相同** |
| Nanally Image | 21,538,400 | **完全相同** |

→ 三个都有，内容一致 → **不是差异。**

### 4.4 ⭐ AK3 anykernel.sh 对比（今天最有价值的发现）

| | 大小 | `rm kernel_dtb` | `patch_cmdline` | 结果 |
|---|---|---|---|---|
| **Jianke** | 793 B | ❌ 无 | ❌ 无 | ✅ 能开机 |
| **Nanally** | 1581 B | ✅ 有 | ❌ 无 | ✅ 能开机 |
| **我们** | 3293 B | ✅ 有 | ✅ **有（×4）** | ❌ 卡一屏 |

**两个结论**：
1. **`rm kernel_dtb` 不是元凶** —— Nanally 也删，能开机。（旧头号嫌疑淘汰）
2. **`patch_cmdline` 是「我们有、两个成功先例都没有」的唯一操作** —— 需重点验证。

### 4.5 打包链无损（已验证，排除「打包损坏数据」）

### 5.2 建议顺序：**先刷 SELFTEST-B**

| 结果 | 结论 | 下一步 |
|---|---|---|
| **B 能开机** | 我们的 **Image 是好的** → 元凶在**我们的打包链**（唯一差异 = `patch_cmdline`） | 去掉 patch_cmdline 重打一版，基本就能开机 |
| **B 仍卡** | 我们的 **Image 有问题**（内核侧），或 (b) 假设 | 刷 A 再确认打包链，然后转内核侧排查 |

**为什么先 B**：它把「我们的打包差异」全部剔除，只留我们的 Image。若它能开机，我们立刻拿到可用路径。

### 5.3 ⚠️ 刷 B 之前必须做的自检（安全）

**Jianke 的 anykernel.sh 用小写 `block=boot` / `is_slot_device=auto`，我们的 AK3 core 用大写 `BLOCK` / `IS_SLOT_DEVICE`。** 今天想核对 Jianke 的 `tools/ak3-core.sh` 是否匹配这个大小写约定，但提取那一步没拿到输出（`grep BLOCK` 返回空）。

**明天刷 B 之前必须先确认**：
```sh
unzip -o -q '.../SELFTEST-B_我们的内核+Jianke的AK3外壳.zip' -d /data/local/tmp/chkB
grep -nE 'BLOCK=|block=' /data/local/tmp/chkB/tools/ak3-core.sh | head
```
- 若 Jianke 版 core 读的是小写 `$block` → 自洽，可刷
- 若不匹配 → `$BLOCK` 为空 → AK3 有 `[ ! -e "$BLOCK" ] && abort` 守卫，**应该安全 abort**，但要确认守卫存在再刷

**另外**：两个自检包的 `anykernel.sh` 都会**自动安装 bootlog-harvester**（SELFTEST-B 用 Jianke 的脚本→无此逻辑；SELFTEST-A 用我们的→有）。刷前留意。

### 5.4 刷入前检查清单（每次刷都要）

## 8. 已经排除的嫌疑（省得重复走）
